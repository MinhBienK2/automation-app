# design-sync notes — automation_app

Repo-specific gotchas for syncing `src/components/ui` to claude.ai/design.
Read this before re-running the sync. Config lives in `.design-sync/config.json`.

## The shape of this sync

- This is an **application** repo, not a component library. The design system is
  `src/components/ui/` (29 files → 55 exported components, counting compound
  subparts like `DialogContent` / `TableRow`).
- `package.json` `main` points at the **Electron main process**, so there is no
  library entry for design-sync to consume, and its synth-entry fallback would
  produce weak `.d.ts` contracts. **`.design-sync/build-ds-pkg.mjs` assembles a
  real one into `.ds-pkg/`** (gitignored, fully regenerated every run — never
  hand-edit it). That script is `cfg.buildCmd`; always run it before the
  converter.
- `.ds-pkg/src/` files are copied into **group directories** (actions, forms,
  data-display, feedback, overlays, navigation). That is the only thing that
  gives the DS pane its grouping — design-sync derives `<group>` from the src
  path, and a flat directory would put all 55 components in `general`. The copy
  step rewrites sibling imports (`./button` → `../actions/button`) to match.
  **Adding a component to `src/components/ui` requires adding it to `GROUPS` in
  build-ds-pkg.mjs** — the script fails loudly rather than mis-filing it.
- Compound subparts (`CardHeader`, `DialogTitle`, `TableRow`, …) don't match a
  file by name, so they'd land in `general` too. They are pinned to their parent
  file via `cfg.componentSrcMap`. A new subpart export needs a new pin.

## Fonts

`src/styles/base.css` names Plus Jakarta Sans / Inter / JetBrains Mono, but the
app ships no font files and renders in system fallbacks (CSP allows
`font-src 'self' data:`). Decision (2026-08-02, user-approved): **vendor the
three families** rather than let every generated design inherit a fallback.

- `.design-sync/fetch-fonts.mjs` downloads the latin subsets from Google Fonts
  into `.design-sync/fonts/` (committed); `cfg.extraFonts` points at the
  generated `fonts.css`.
- All three are **variable** fonts — one woff2 per family covering a weight
  range. Do not "fix" the script to request discrete weights; that returns the
  same file once per weight (324 KB instead of 120 KB).
- This makes the DS pane render slightly crisper than the app itself. The app
  was deliberately left untouched.

## Known render warns (triaged — not new)

- `[FONT_MISSING] "Source Code Pro", "Office Code Pro", "Cambria"` — these are
  **fallback-chain entries** inside `--font-mono` and Tailwind's default
  `--font-serif`, not brand faces. The primaries all ship. Accepted, do not
  chase.
- `tokens: 2 missing` — below the converter's own threshold, non-blocking.

## Preview harness

- **`DSPreviewRoot`** (`.ds-pkg/preview-root.tsx`, generated by build-ds-pkg,
  wired as `cfg.provider` + `cfg.extraEntries`) wraps every preview. It exists
  because design-sync's card template hard-codes `body{background:#fff}` while
  this DS is dark-first with near-white text — without it, form controls and
  labels render invisible and the render check reports blank/thin cards. It
  reproduces the app's own `body` rule from `src/styles/base.css`.
- The app picks dark vs light with a `data-theme` attribute on `<html>` set by
  `src/app/useThemePreferences.ts`. With no attribute the tokens are the **dark**
  values, which is what previews and generated designs get.
- **Authored previews must use inline `style={{…}}` for layout glue, never
  Tailwind utility classes.** The compiled stylesheet is produced by
  `build-ds-pkg.mjs`; a utility appearing only in a preview file won't be in the
  CSS unless that step reruns, and the per-component `preview-rebuild.mjs` path
  (which subagents use) doesn't rerun it. Referencing DS tokens inline
  (`var(--surface)`, `var(--accent)`, `var(--font-mono)`) is fine.
- `cfg.overrides.DataTable = {"cardMode": "column"}` — the run table renders
  wider than a grid cell and gets cropped otherwise.

## Defects this sync found and fixed in `src/` (2026-08-02, user-approved)

Authoring previews for all 32 components surfaced three real bugs in the app —
all verified against the app's own built stylesheet, not just the harness.

1. **`--border` token collision (`src/styles/base.css`).** The DS defines
   `--border` as a *colour* unlayered at `:root`; daisyUI defines it as a border
   *width* inside `@layer base`. Unlayered wins, so daisyUI's
   `border: var(--border) solid …` shorthand is invalid on
   `.btn/.input/.select/.textarea/.checkbox/.badge`, and `.toggle`'s width
   `calc()` collapses the switch to **8×24px** (measured; should be ~40×24).
   Fixed narrowly with `.toggle { --border: 1px; }` next to the existing toggle
   overrides — a declaration matching the element beats the value inherited from
   `:root`, in both themes. **The other components are unaffected today only
   because base.css re-declares their borders with `!important`.** The
   architecturally correct fix is renaming the colour token to `--border-color`,
   but `var(--border)` has 132 usages across 12 files, so it was deliberately
   deferred. If a daisyUI component ever loses its border for no obvious reason,
   this is why.
2. **`SearchInput`'s magnifier icon painted behind the input.** The icon div is
   `absolute left-3` and precedes `<Input>`; daisyUI's `.input` is
   `position: relative` with an opaque background, so the later sibling covered
   it. Fixed with `z-10` on the icon wrapper. Also affected `Select searchable`,
   which embeds SearchInput. (Note when re-testing: the icon is
   `pointer-events-none`, so `elementFromPoint` will always report the input —
   verify by pixel, not by hit-test.)
3. **`.badge-outline` had no visible border.** `.badge` forces
   `border: 1px solid transparent !important` and every variant restores a
   border-color except `outline`. Fixed by adding a `.badge-outline` rule. This
   is a *different* root cause from #1 despite looking similar.

`npx vitest run src/AppCss.test.ts src/components/ui/` (60 tests) passes after
all three. `npm run lint` reports 2 warnings, both pre-existing in
`electron/backend/` and unrelated.

## OPEN finding — deliberately not fixed

**~42 Tailwind colour utilities in `src/` resolve to nothing.** `bg-surface`,
`bg-surface-elevated`, `text-fg-primary`, `text-fg-secondary`, `text-fg-muted`
and friends are used across `empty-state.tsx`, `form-field.tsx`,
`page-header.tsx`, `table.tsx`, `section-card.tsx`, `confirm-dialog.tsx`,
`search-input.tsx` and several `src/features/**` files — but **no `@theme` block
maps `--color-surface` / `--color-fg-primary`**, so Tailwind never generates
them. Verified in a browser against the compiled sheet: `text-fg-primary`,
`text-fg-secondary` and `text-fg-muted` all compute to the *same* colour, and
`bg-surface` is `rgba(0,0,0,0)`.

It goes unnoticed because the inherited `body` colour is close to the intent —
but the intended text hierarchy is not actually rendering anywhere in the app.

Not fixed because adding the `@theme` mapping would activate ~42 dormant class
usages simultaneously, i.e. a real visual change across the product — an
app-design decision, not a sync decision. **If someone adds that mapping later,
re-run the sync**: component appearance will shift and every render hash will
change.

The conventions header (`.design-sync/conventions.md`) explicitly instructs the
design agent never to use these class names and to reach the token layer through
`var(--token)` arbitrary values instead, which is what actually works.

## Component quirks worth knowing (from the authoring waves)

- **`Tooltip`'s bubble cannot be captured statically.** `TooltipContent` renders
  `null` and only feeds context; `TooltipTrigger` accepts no `className`, so
  daisyUI's `tooltip-open` escape hatch is unreachable through the public API.
  Tooltip and IconButton cards show the wired composition, never the bubble.
- **`DropdownMenu` has no declarative open API** — open state is internal
  `useState`, and daisyUI additionally requires `:focus-within`. Its preview
  uses an `OpenOnMount` helper that calls `trigger.focus(); trigger.click()`.
  A `defaultOpen` prop (mirroring `Dialog`'s `open`) would remove the
  workaround; not added, as it's a `src/` API change.
- **`Select`'s open dropdown is not captured** — it's `<details>`-based and the
  option list would overflow the cell. Only closed-trigger states are graded.
- **`ToastProvider` toasts ARE capturable** by calling the exported `useToast()`
  in a mount `useEffect`; they survive the 4s auto-dismiss. Keep cell body
  content narrow (~200px) or the `toast-top toast-end` stack overlaps it.
  Reuse this pattern for other imperative-only components.
- `Switch` requires `checked` + `onCheckedChange`; `Checkbox` makes both
  optional and supplies its own `onChange`.
- `Label` is `display: grid` and the repo's canonical form *wraps* its control
  rather than using `htmlFor`.
- `Button` has no `outline` variant (`default | secondary | ghost |
  destructive`) — `secondary` is the outlined one. Easy trap when porting
  shadcn-shaped markup.
- `DialogContent` injects `max-w-lg` unless the className carries a `max-w-*`;
  widen with inline `style={{ maxWidth: … }}`, which lands on `.modal-box`.
- `SectionCard` has no usages anywhere in `src/` — its stories were authored
  from the API plus app vocabulary, not ported.
- `UnsavedChangesDialog`'s action row wraps "Keep editing" onto a second line at
  the dialog's own `min(480px, …)` width. Shipped CSS, not a preview artifact.

## Card-mode overrides and why each exists

- `DataTable → column` — its 6-column run table renders wider than a grid cell.
  `Table` / `SortableTableHead` do NOT need this: 3-4 columns fit. Add it only
  if a story grows past ~5 columns.
- `Dialog`, `ConfirmDialog`, `UnsavedChangesDialog → single` — they portal to
  `document.body` with a full-viewport `.modal` + backdrop, so the default grid
  card stacks every export on one fixed layer and shows only the last over N
  backdrops. Per-story capture (used for grading) is unaffected — this only
  breaks the product's live card.
- `PageHeader` needs no override: an inner `maxWidth: 720` is sufficient.

## Environment

- **No bundled chromium.** The render check and capture both need
  `DS_CHROMIUM_PATH=/usr/bin/google-chrome` in the environment. Playwright is
  importable (via the repo's `@playwright/test`), only the browser binary is
  missing, and the ~200 MB download is unnecessary because system Chrome works.
- Converter deps live in `.ds-sync/` (esbuild, ts-morph, @types/react, and
  `@tailwindcss/cli` which build-ds-pkg.mjs invokes). Re-copy the staged scripts
  and re-install on a fresh clone.

## Scope decisions

- Rich authored previews cover the **32 standalone components**. The 23 pure
  compound subparts ship the floor card deliberately: they only render
  meaningfully inside the parent composition, which already has a card. They are
  fully importable with real prop contracts. Authoring them is a standing offer
  for any later re-sync.
- `src/components/layout/` is **out of scope** (user decision). Note that it has
  its own `PageHeader`, colliding with `ui/page-header.tsx` — pulling layout in
  later requires resolving that name clash via `cfg.componentSrcMap`.

## Re-sync risks — what can silently go stale

- **`GROUPS` in build-ds-pkg.mjs and the `componentSrcMap` pins are manual
  mirrors of the source tree.** New components fail the build loudly (good), but
  a new *subpart* export just lands in `general` quietly. Check the group
  listing after any change to `src/components/ui`.
- **The vendored fonts are a point-in-time download.** Google may reissue the
  woff2; re-running `fetch-fonts.mjs` changes bytes and invalidates render
  hashes. Only re-run when adding a family or weight range.
- **The compiled `styles.css` is regenerated from the app's real Tailwind
  source**, so any app-wide style change lands in the DS bundle too — including
  changes that have nothing to do with the UI kit. That is intended (the token
  layer is shared), but a surprising visual diff on re-sync usually traces to
  `src/styles/*.css`, not to a component.
- **`.ds-pkg/` is gitignored and rebuilt from scratch.** Nothing in it is
  durable; never put a fix there — put it in `build-ds-pkg.mjs`.
- The tsc declaration step tolerates diagnostics and only fails if
  `dist/index.d.ts` is absent. If prop contracts ever look wrong, read the tsc
  output rather than trusting the exit path.
