# Mission Control Evidence Explorer Design

Date: 2026-05-27

## Status

Approved design for a written specification on 2026-05-27.

This is specification 3 of the Mission Control production adoption program. It
is ready for user review before the remaining program specifications are
written. Per the approved program gate, no implementation planning or
production code changes begin until all program specifications are written and
approved.

## Goal

Add `Evidence` as the durable investigation workspace for evidence generated by
workflow runs. Operators must be able to find, inspect, safely reveal and
export evidence across persisted runs without exposing raw browser storage,
unsafe filesystem paths or unclassified output payloads.

The completed feature must:

- Provide a real Evidence Explorer workspace in the Mission Control shell.
- Investigate evidence from persisted history across multiple runs, rather
  than only current-process session snapshots.
- Treat both generated file artifacts and approved structured evidence as
  first-class, typed investigation items.
- Preserve workflow, run, step, run-source and historical browser-identity
  traceability after restart or later identity rotation.
- Keep all filesystem interaction inside validated Electron/backend commands.
- Export a sanitized, auditable evidence bundle for selected items.
- Extend the operations read boundary approved in specification 2 without
  introducing an unnecessary evidence projection table.

The Mission Control program is specified in this order:

## Existing Product Boundary

Current production code already provides:

| Source | Available Capability |
| --- | --- |
| SQLite `runs` | Durable run status, start/finish timestamps, workflow settings and graph snapshots, sanitized outputs and errors. |
| SQLite `run_steps` | Durable top-level and nested executed step/action trace rows. |
| Persisted output `__evidence` | Structured metadata for generated screenshot and download artifacts, including safe run-scoped relative paths. |
| Persisted output `browser_identity` | Sanitized browser identity evidence for the run. |
| Persisted output `__action_traces` | Structured action execution traces and compact evidence/output summaries. |
| Persisted output `__evidence_model` | Category, size, redaction and truncation manifest for outputs. |
| Evidence directory helpers | Run-scoped artifact path creation and containment enforcement under `evidence/runs/<run_id>/...`. |
| Workflow settings snapshot | Browser Launch identity state used at run start. |
| Schedule events | Durable schedule audit rows with `run_id` where a scheduled occurrence started a run. |

Current production code does not provide:

- A renderer-facing evidence query/detail API.
- A standalone `Evidence` route.
- Safe screenshot preview, artifact reveal or evidence-bundle export actions.
- Durable run-source provenance on the `runs` table; `manual` versus
  `schedule` currently exists only on in-process run snapshots.
- Broad evidence browsing from Overview or Runs.

## Chosen Approach

Use **Evidence Read Model + Validated Artifact Command Boundary**.

The Electron backend owns a bounded evidence read service over persisted runs,
run steps, workflow metadata and already-sanitized persisted outputs. It
generates typed evidence items and stable references without writing a second
evidence catalog. The renderer owns filters, selection and presentation.
Preview, reveal and export commands remain backend/native operations that
resolve and validate artifact references before touching local files.

This approach was selected over:

| Alternative | Reason Not Chosen |
| --- | --- |
| Materialized `evidence_items` projection table | Adds migration, backfill and reconciliation behavior without an established query-volume or latency need. Existing durable outputs already contain the required truth. |
| Artifact-only Explorer | Omits browser identity, action traces and redaction/truncation evidence needed for investigation. |
| Raw output browser in the UI | Exposes unnecessarily broad output data and expands sensitive-data review beyond the approved evidence model. |

## Scope

### Included

- New `Evidence` route/page in the Mission Control shell.
- Sidebar order after this phase: `Overview`, `Workflows`, `Runs`,
  `Evidence`, `Schedules`, `Settings`.
- Evidence list/search/filter/pagination across persisted run data.
- File artifact item types: `screenshot` and `download`.
- Structured evidence item types: `browser_identity`, `action_trace` and
  `evidence_manifest`.
- Detail presentations appropriate to each supported evidence type.
- Validated screenshot preview, file reveal and sanitized bundle export
  commands.
- Navigation from Evidence to a selected durable run in `Runs` and to the
  related workflow when it still exists.
- Navigation from Overview `Recent Evidence` directly to selected evidence
  after this phase exists.
- `Open Evidence` from a focused run in `Runs`, opening Evidence filtered to
  that run.
- Persistence of durable `runs.source` provenance for historical filtering.
- Historical identity association from the identity used at run time.
- Bounded handling of malformed evidence metadata and unavailable artifact
  files.

### Excluded

- Raw arbitrary page-output browsing or free-form JSON output inspection.
- Separate evidence item types for logs or challenge observations unless a
  later specification adds a durable typed evidence contract for them.
- Browser storage, cookies, tokens, credentials, proxy secrets or unsanitized
  filesystem locations.
- Opening or rendering downloaded files in the application.
- `Identities` navigation, identity diagnostics, identity editing or identity
  reset actions.
- Evidence delete, purge, retention-policy authoring, annotation, tagging,
  cases, incident workflow or collaboration features.
- Changes to runner evidence generation semantics or new graph actions.
- Materialized evidence indexing or centralized/multi-machine evidence
  aggregation.

### Ownership Rules

- `Evidence` owns evidence listing, cross-run investigation, evidence detail,
  safe artifact operations and export.
- `Runs` owns execution monitoring and the bounded selected-run detail receiver
  approved in specification 2; it does not gain a historical evidence browser.
- `Overview` owns summary metadata and operational triage; after Evidence is
  available, selecting a Recent Evidence item opens Evidence focused on the
  referenced `evidence_id`.
- `Workflows` remains the working destination for opening the related workflow
  or Graph Builder.

### Supported Navigation

| Origin | Action | Destination |
| --- | --- | --- |
| Overview Recent Evidence item | Select/open item | Evidence with `evidence_id` focus target. |
| Runs focused durable run detail | `Open Evidence` | Evidence filtered by `run_id`. |
| Evidence detail | `Open Run` | Runs focused durable-run receiver for the item run. |
| Evidence detail | `Open Workflow` | Existing workflow/detail destination when the workflow still exists. |

Evidence displays historical `identity_id` and display context but does not
render a disabled or placeholder `Open Identity` action before specification
4.

## Durable Run Source Provenance

### Schema Addition

Evidence investigation must distinguish operator-started runs from scheduled
runs after an app restart. The `runs` table gains:

```text
source TEXT NOT NULL CHECK (source IN ('manual', 'schedule'))
```

The persistence layer also adds:

```text
CREATE INDEX idx_runs_source_started_at ON runs(source, started_at DESC)
```

This index supports durable source/time filtering without requiring a
materialized evidence table.

The source is stored when a run row begins:

- Graph Builder and workflow-list full runs persist `manual`.
- Existing operator-started batch executions, when represented by run rows,
  persist `manual`; this specification does not introduce a third source
  category.
- Scheduler-started workflow runs persist `schedule`.

### Existing Row Migration

For local rows that predate the new column:

1. Backfill `schedule` only when a persisted
   `workflow_schedule_events.run_id` positively associates the run with a
   started scheduled occurrence.
2. Backfill every other legacy run as `manual`.

This migration is deterministic and does not claim missing schedule
provenance when no durable schedule-event relation exists.

### Schedule Reference

When an evidence item's run has a related schedule-event row, the read model
may provide that safe schedule reference for traceability. It does not copy a
full schedule snapshot into the run or make schedules part of Evidence
editing.

## Evidence Read Model

### Evidence Item Sources

The read model derives supported items from each persisted run:

| Persisted Data | Evidence Item | Cardinality Per Run |
| --- | --- | --- |
| Each valid `__evidence` artifact metadata object | `screenshot` or `download` | One per unique safe artifact reference. |
| Valid `browser_identity` object | `browser_identity` | Zero or one. |
| Valid non-empty `__action_traces` collection | `action_trace` | Zero or one timeline item. |
| Valid `__evidence_model` manifest | `evidence_manifest` | Zero or one. |

Page observations, arbitrary output keys and operator inputs do not become
standalone list items. Their category/redaction/truncation presence is
represented through the evidence manifest and any existing compact action
trace summaries.

### Stable Evidence Identifiers

Existing artifacts do not carry standalone database ids. Evidence references
are deterministic opaque values produced by the backend:

| Kind | Identity Inputs |
| --- | --- |
| `screenshot` / `download` | `run_id`, artifact kind and validated safe relative artifact path. |
| `browser_identity` | `run_id` and fixed `browser_identity` discriminator. |
| `action_trace` | `run_id` and fixed `action_trace` discriminator. |
| `evidence_manifest` | `run_id` and fixed `evidence_manifest` discriminator. |

Duplicate artifact metadata producing the same identifier appears once. An
`evidence_id` is a UI/read-model reference; it does not rename files or alter
persisted run outputs.

### Historical Relationships

Each item carries:

- Related `run_id`, status, persisted source, start/finish timing.
- Related workflow id and current display name when the workflow still exists.
- Node id and step number where artifact metadata supplies them.
- Historical browser identity metadata derived only from the run's
  `settings_snapshot_json.browser_launch` and sanitized `browser_identity`
  output.
- Schedule reference only when safely derivable from an existing
  schedule-event relation.

Identity display/filter behavior is based on the run-time snapshot. A later
workflow identity rename or rotation must not relabel old evidence as though
it was created by the new identity.

### Malformed Data

The read model validates structured values before converting them to typed
items. Invalid evidence objects are skipped. Responses report a bounded
warning summary such as counts of skipped artifact/report/trace/manifest
items; they never return malformed raw payloads to explain the warning.

## Query And Detail Contracts

### Evidence List Query

The renderer uses one bounded list command, conceptually:

```text
listEvidenceItems({
  search?,
  types?,
  run_statuses?,
  sources?,
  workflow_id?,
  run_id?,
  identity_id?,
  time_start_utc?,
  time_end_utc?,
  cursor?,
  limit?
}) -> EvidencePage
```

Supported filtering behavior:

| Filter | Meaning |
| --- | --- |
| `search` | Case-insensitive search over workflow display name, run id, node id, historical identity id/display name and safe relative artifact path/typed label. It does not search raw output values. |
| `types` | One or more supported evidence item kinds. |
| `run_statuses` | Persisted run terminal/current status values returned by the run contract. |
| `sources` | Durable `manual` and/or `schedule` values from `runs.source`. |
| `workflow_id` / `run_id` | Exact traceability target filters. |
| `identity_id` | Exact historical run-time identity id filter. |
| Time range | Inclusive lower, exclusive upper UTC timestamp bounds applied to the item ordering timestamp. |

`EvidencePage` conceptually returns:

```text
EvidencePage {
  generated_at
  items: EvidenceListItem[]
  next_cursor: string | null
  has_more: boolean
  warnings: {
    skipped_artifacts: number
    skipped_reports: number
    skipped_traces: number
    skipped_manifests: number
  }
}
```

### Ordering And Pagination

Items are ordered by `(created_at DESC, evidence_id DESC)`. For file artifacts,
`created_at` uses validated artifact metadata. For structured evidence, it
uses run finish time when present and run start time otherwise. If a valid
artifact lacks a valid created timestamp, it falls back to the same run
finish/start timestamp.

The command uses an opaque cursor encoding the last ordering tuple. The
default page size is 50 items; the backend clamps any requested limit to 100.
The renderer does not request all history at once.

### List Item Shape

Each list result is a safe summary:

```text
EvidenceListItem {
  evidence_id
  kind: "screenshot" | "download" | "browser_identity" | "action_trace" | "evidence_manifest"
  label
  created_at
  run: { id, status, source, started_at, finished_at? }
  workflow: { id, name } | null
  identity: { id, display_name? } | null
  node_id?
  step_number?
  relative_path?
  file_state?: "unchecked" | "available" | "unavailable"
  navigation_targets: { run: true, workflow: boolean }
}
```

List loading does not need to read every artifact file from disk. File items
can initially return `unchecked`; preview, reveal or export resolves the
authoritative file state.

### Evidence Detail

The renderer loads detail only for the selected item:

```text
getEvidenceDetail(evidence_id) -> EvidenceDetail
```

The detail response includes the list metadata, traceability fields and
exactly one typed safe payload:

| Item Kind | Detail Payload |
| --- | --- |
| `screenshot` | Artifact metadata and latest checked file state; image bytes are obtained through the preview command only. |
| `download` | Artifact metadata plus validated file state and, when available, bounded file size/type metadata; no file contents. |
| `browser_identity` | Sanitized run-time identity report field/value structure. |
| `action_trace` | Bounded ordered timeline of node/step/action status, timestamps, audit tags and compact output/evidence summaries. |
| `evidence_manifest` | Manifest rows with output key, category, approximate bytes, redacted flag and truncated flag. |

Action-trace detail is capped at 500 entries. If more traces exist, the
response reports truncation; this specification does not create unbounded
trace export through the UI.

The detail API never returns raw settings snapshots, raw arbitrary outputs,
browser storage, proxy credentials, absolute local paths or malformed
unvalidated structures.

## Artifact Command Boundary

### Path Validation Rule

The renderer sends only `evidence_id`. For any command that reads or copies a
file, the backend:

1. Resolves the evidence item from persisted safe metadata.
2. Verifies it is a file artifact kind.
3. Revalidates that its relative path is a run-scoped path under
   `runs/<run_id>/...`.
4. Resolves it beneath the application's configured evidence directory.
5. Rejects traversal, absolute paths, missing item references and mismatched
   run identifiers.
6. Checks file existence/readability for the requested operation.

An absolute path is used only inside backend/native code; it is not serialized
to the renderer.

### Screenshot Preview

```text
getEvidenceScreenshotPreview(evidence_id) -> {
  evidence_id
  mime_type: "image/png"
  base64_data
  file_state: "available"
}
```

The command accepts only a validated `screenshot` item and a readable
run-scoped screenshot file. It returns a PNG preview payload for display inside
the app only when the source image is no larger than 10 MiB. A larger readable
screenshot remains an available artifact but returns a serializable
`preview too large` error and is still eligible for reveal/export. A missing
or unreadable file returns a serializable `file unavailable` error so the
detail panel can update the item state.

### Download Behavior

Downloads appear with metadata only. Evidence Explorer does not provide a
download preview, execute, open-file or embedded renderer command. Download
files can be revealed in their system folder or included in an explicit
evidence bundle after validation.

### Reveal In Folder

```text
revealEvidenceArtifact(evidence_id) -> void
```

This native Electron action is available only for a validated readable
`screenshot` or `download`. It reveals the artifact in its containing folder;
it does not open or execute the file. An unavailable file yields a local
detail-panel error and disables reveal until refreshed.

### Copy Relative Path

`Copy Relative Path` exists only for file artifacts and copies the safe
relative path already present in its typed DTO. It never copies or requests an
absolute path.

## Evidence Bundle Export

### Export Command

```text
exportEvidenceBundle({
  evidence_ids: string[]
}) -> EvidenceBundleExportResult | null
```

Selection contains supported evidence references only. The Electron/native
boundary asks the operator to select a destination directory. If the operator
cancels, no files are written and the renderer preserves the current
selection.

Inside the selected destination, the backend creates a new uniquely named
bundle directory using an UTC timestamp and a numeric suffix on collision; it
does not silently overwrite a prior bundle. The bundle layout is:

```text
evidence-bundle-<UTC timestamp>/
  manifest.json
  artifacts/
    <copied readable selected file artifacts>
```

No archive/ZIP dependency is introduced by this specification.

### Manifest Contents

`manifest.json` is sanitized and includes:

- Schema/version identifier and export generation timestamp.
- Selected evidence ids and item kinds.
- Workflow/run/step references.
- Persisted run status/source and timing.
- Historical safe identity reference/display label where present.
- Artifact relative paths and copied-file bundle-relative paths.
- Structured evidence detail for identity report, action trace and evidence
  manifest items, bounded exactly as the UI detail contract.
- Redaction/truncation flags.
- `file_unavailable` or omitted-file entries for selected artifacts that were
  missing or unreadable during export.

The bundle does not include:

- Absolute original filesystem paths.
- Raw unclassified outputs.
- Browser storage, cookies, credentials or proxy secrets.
- Missing/unreadable artifact file contents.

### Partial And Fatal Export Failure

Every selected item is revalidated during export. A selected artifact file
that is unavailable does not fail the entire export; it is represented as
unavailable in the manifest and the UI reports that the completed bundle has
omissions.

Failure to create the bundle directory, write `manifest.json` or copy an
otherwise validated readable selected file is a command failure. The UI
reports that the export did not complete successfully rather than claiming a
complete bundle.

## Evidence Explorer UI

### Page Layout

Evidence Explorer uses the Mission Control design system from specification 1:

- Page title `Evidence Explorer`.
- Compact command bar with refresh and `Export Selection`.
- Search field and filter controls.
- Segmented `Grid` / `List` view control.
- Results workspace.
- Selection-aware detail panel on desktop.
- Detail drawer at compact widths.

The page is an operational tool surface, not a landing page. It does not
include visible explanatory marketing or feature-instruction text.

### Results And Filters

- Default sort is most recent evidence first.
- `List` mode is dense and scanning-oriented.
- `Grid` mode is available for visual evidence selection, with screenshot
  preview/thumb emphasis only when a validated preview has loaded.
- At compact width the results prioritize list presentation and detail opens
  in a drawer to preserve available scanning width.
- Filters expose evidence type, run status, durable run source, workflow,
  historical identity and timestamp range, each mapped directly to the
  corresponding list-query field.
- Search does not imply full-text inspection of raw outputs.

### Detail Variants

| Selected Kind | Presentation |
| --- | --- |
| Screenshot | Validated preview, artifact metadata, workflow/run/node/identity traceability and file actions. |
| Download | File icon/type/size/path/status metadata and traceability; no content preview. |
| Browser Identity Report | Read-only sanitized technical fields tied to the run-time identity. |
| Action Trace | Ordered step/action timeline with statuses, timestamps, audit tags and compact summaries. |
| Evidence Manifest | Table of categories/output keys/approximate size and explicit redacted/truncated labels. |

Color is never the only evidence/status indicator. Technical identifiers and
paths use the technical typography role; destructive styles are not used
because this page introduces no evidence deletion.

### Selection And Actions

- Selecting an item loads its detail without changing the current list filter
  state or cursor context.
- Multi-select is used only for `Export Selection`.
- `Open Run` exists for every supported item.
- `Open Workflow` is enabled only when the related workflow still exists.
- `Copy Relative Path` and `Reveal in Folder` exist only for file artifacts.
- Screenshot preview actions exist only for screenshot items.
- There is no `Open Identity` action until specification 4 is implemented.

### Empty, Warning And Error States

- A legitimate zero-result filter displays an honest no-results state.
- A list-query failure displays a page-level error with retry and keeps filter
  state; it does not substitute zero results.
- A detail, preview or reveal error appears in the detail panel/drawer without
  preventing list browsing.
- Malformed persisted evidence is omitted and reported through a restrained
  skipped-item warning based only on safe counts.
- Metadata for a valid artifact remains visible when its physical file is
  unavailable. The item displays `File unavailable`, disables preview/reveal
  until a later refresh, remains navigable and remains eligible for manifest
  reporting during bundle export.

## Refresh And Runtime Behavior

- Evidence loads when the workspace opens.
- Changes to search, filters or cursor request the corresponding bounded page.
- Manual refresh reruns the current query and resets resolved availability
  states from backend truth.
- If the renderer observes a currently tracked run transition to a terminal
  state while Evidence is open, it refreshes the current result query once so
  newly completed evidence can appear.
- Evidence does not poll full persisted history on the existing rapid run
  snapshot interval.
- Preview and detail are loaded only as needed for the current selection.

## Ownership And Integration Boundaries

| Owner | Responsibility |
| --- | --- |
| Persistence schema/migration | Add/backfill/index durable `runs.source` required for source filtering. |
| Evidence read-model backend service/repository | Typed extraction, validation, filtering, ordering, pagination, deduplication, malformed-data warnings and historical references. |
| Existing run-start boundary | Persist correct `manual` or `schedule` source when the run row is created. |
| Electron/native command boundary | Path-validated preview/reveal and native destination evidence-bundle export. |
| IPC/preload/wrapper/type boundary | Typed list/detail/preview/reveal/export commands and serializable errors. |
| New Evidence page/components | Workspace filters, selection, detail variants, action availability, warnings/errors and compact drawer. |
| Overview page | Open selected evidence focus target once Evidence exists. |
| Existing Runs page | Provide `Open Evidence` for a focused run while retaining its execution-monitor responsibility. |

The renderer must not import filesystem, SQLite, Electron shell/dialog or Node
APIs directly.

## Security And Privacy Constraints

- Evidence browsing is limited to already persisted, authorized run evidence.
- Backend evidence DTOs return only safe typed metadata or specifically
  approved sanitized structures.
- The application must not disclose absolute evidence paths to renderer
  consumers.
- File commands revalidate path containment and file state at the command
  boundary; renderer-provided strings cannot name arbitrary files.
- Download files are never automatically opened, executed or rendered.
- Raw page outputs, storage values, credentials, proxy secrets and sensitive
  unclassified material remain unavailable through Evidence IPC.
- Bundle export preserves redaction/truncation state and does not claim missing
  file contents were exported.

## Acceptance Criteria

This specification is successfully implemented when:

- `Evidence` is a working sidebar destination placed between `Runs` and
  `Schedules`; `Identities` remains absent until its own implementation.
- Evidence Explorer reads durable cross-run history through bounded backend
  DTOs, not current-session state or renderer-side SQLite/filesystem access.
- Persisted `runs.source` truthfully supports historical `manual`/`schedule`
  filtering with deterministic migration of existing rows.
- The Explorer provides supported file and structured evidence item kinds
  without exposing raw arbitrary output browsing.
- Search/filter/cursor pagination is typed, bounded and stable.
- Evidence remains tied to historical run-time identity context even after
  workflow identity changes.
- Screenshot preview and artifact reveal occur only after backend path/file
  validation; downloads are never rendered or automatically opened.
- Overview and Runs navigate to Evidence according to their approved ownership
  boundaries, and Evidence navigates back to a selected run or existing
  workflow.
- Export Selection produces a sanitized manifest-based evidence bundle,
  preserves redaction/truncation and unavailable-file reporting, and excludes
  absolute paths, secrets and raw unclassified outputs.
- Missing files or malformed persisted evidence produce truthful local warning
  states without destroying valid audit metadata or claiming successful file
  availability.
- Required tests, documentation sync and desktop/compact visual verification
  pass during implementation.
